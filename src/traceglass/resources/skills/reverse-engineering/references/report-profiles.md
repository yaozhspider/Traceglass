# 按任务组织的报告交付规范

统一分析助手依据用户本次要求选择报告类型；不要依据样本文件名、工具标签或“恶意”字符串命中猜类型。静态逆向用 `binary`，恶意软件分析用 `malware`，行为核查用 `behavior`，加解密分析用 `crypto`。跨主题任务以用户的主要问题为主，其他发现放入相关章节的三级小节。普通追问直接回答，不为每次回复生成整份报告。修订已有报告时沿用原报告类型，除非用户要求改变分析目标。

正式交付前用 `validate_reverse_report(report=完整正文, report_type=所选类型)` 或 `save_analysis_artifact(artifact_path="report.md", content=完整正文, report_type=所选类型)` 保存。校验器、自动修复和正式交付使用同一类型。标题采用 `# 样本名称 逆向分析报告`、`# 样本名称 恶意软件分析报告`、`# 样本名称 行为核查报告` 或 `# 样本名称 加解密分析报告`。auto 仅根据完整标题的精确后缀选择；不识别的历史标题仍按 binary 检查。不要在面向人的报告中解释这些内部参数。

## 先让读者看懂判断

在“执行摘要”中先用一句通俗中文回答本次问题，再列出紧凑决策表：

| 项目 | 内容 |
|---|---|
| 核心判断 | 根据已取得的证据能确认什么，不能确认什么 |
| 置信度 | 高/中/低，附支持强度、冲突或缺口的具体理由，不编造百分比 |
| 关键依据 | 最多 3–5 项，每项带真实证据引用；发现更少时按实际数量写 |
| 主要限制 | 最影响结论的未覆盖路径、缺失组件或未执行验证 |
| 下一步 | 按影响排序的可执行复核或处置建议，注明适用条件 |

主体按“发现 → 为什么这样判断 → 关键证据 → 限制/下一步”组织。每个关键发现使用简短结论句作为三级标题；紧跟短段落或紧凑表格，不堆满地址和 API 名称。技术术语首次出现时解释其实际行为。使用“已观察”“静态支持”“待验证”等明确状态，区分能力、执行尝试、执行成功。标题下有非空内容不等于事实可信。

重要地址、参数、时间和 E-ID 只保留解释结论所需的部分；完整反编译、长工具日志、数据清单和解析输出保存到代码/结果附件，并在附录引用实际文件。正文不贴大段终端输出，不按工具调用顺序写流水账。所有报告均列明样本哈希和范围；未知字段明确写未取得。证据引用应能追溯到真实调用或工件；不要创造路径、编号、输出或已执行实验。

## 不同任务的内容重点

### 静态逆向

回答“程序如何工作”。按入口与分发、关键调用链、核心机制、数据/算法解释实现；保留原有 binary 章节。危险 API 命中不直接等于恶意。复杂函数、线程、回调和难以恢复的分支属于必要覆盖范围，不能以大量辅助函数摘要代替核心链分析。

### 恶意软件分析

回答“有哪些可疑行为，证据能支持多大风险”。“风险判断与关键证据”使用发现、触发条件、观察状态、风险影响、证据和置信理由表。不能因工具未命中、没有动态联网或签名存在就判定安全；证据不足时明确写“尚不足以判定”，不要强行二分类。

“可疑能力与攻击链”围绕有证据的发现组织，分别说明执行、注入、数据访问、规避等实际能力与推断边界；攻击链中未验证的连接标为推测。“持久化与执行触发”说明位置、权限、触发条件以及尝试/成功状态。“网络行为与 IOC”区分静态字符串、解析配置、实际连接和可用于检测的指标，表格列值、类型、来源、上下文、验证状态及误报限制，不把库名/公共域名默认当作恶意 IOC。“验证结果与处置建议”注明静态/动态证据是否一致、观察窗口及隔离条件；未经验证的行为不写成已发生，处置建议与实际风险及证据匹配。

### 行为核查

回答“在什么条件下发生了什么”。先明确待核查假设、输入、隔离环境、观察窗口；未运行时写清楚，不能编造时间线。“行为时间线与触发条件”按因果与事件先后呈现，时间戳仅用真实记录；缺少时间时用调用链并标注静态推断。“系统副作用与数据流”列操作对象、前置条件、尝试/成功、输入输出和证据。“静态推断与动态观察对照”列假设、预期、实际观察、判定及替代解释。未观察到某行为仅能限定于已测条件。“风险影响与复现结论”先回答原假设是否得到支持，再说明可重复性和外推限制。

### 加解密分析

回答“数据如何变换，以及恢复/验证到了哪一步”。“算法识别与依据”区分常量/字符串候选、代码模式、实际验证，不因单个常量宣称确认算法。“密钥、配置与数据流”追踪输入、密钥来源、IV/nonce、模式、填充、字节序、编码与输出去向，未恢复字段不补猜。“实现细节与安全边界”说明边界条件、验证/认证逻辑和适用输入。“复现实验与验证结果”引用实际保存的脚本、命令和结果，给出输入输出比较以及失败/反例；脚本未执行时显式注明。密钥恢复、格式解析、解密成功和完整性校验通过分别判定。

## 覆盖缺口与附件

所有类型均需说明“已分析、部分分析、未评估、不适用”及理由。未评估/不适用章节写具体原因、结论影响和可判定的后续验证，不能只填占位词；无需为填满章节启动额外实验。报告状态 ready 只代表结构检查通过。

附录统一列真实证据 ID、支撑发现、地址/来源、文件路径、已有哈希和复现方法。模型编写的代码保存为独立脚本，解析出的数据保存为独立 JSON/CSV/文本文件，正文链接到这些文件；已执行脚本同时保留实际输入、执行命令、退出状态和结果。未执行代码注明“保存但未执行”。源码和结果分开，长内容不挤进报告正文。不要修改历史报告来适配新模板。
