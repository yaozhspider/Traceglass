# 静态分析、补丁与变体（本地摘录）

## 两层静态工具

**Semgrep** 看语法模式，快，适合「危险 API 的用法」和能在一个函数里说清的规则。改一条规则可以扫很多仓库。它的符号传播能把同一函数里的表达式跟到下一个调用，但中间隔着条件时会丢。对反编译伪代码，正则函数名可以抓到 `malloc` 的各种包装；跨过程的值仍会漏。

**CodeQL / Joern** 把代码变成可查询的数据库，适合「不可信输入能否到达这个 sink」。变体分析用它，不用 grep。代价是要能构建数据库。构建失败时，退回 Semgrep 加人工读调用者，不要假装数据流已经证明可达。

规则写法：源是不可信入口（请求参数、文件块、消息字段），sink 是敏感操作（命令、查询、路径、拷贝、分配大小、反序列化）。中间的 sanitizer 必须是真正消除危险的那种（参数化查询、规范化后的根目录检查），不是任意一个 `if`。

命中之后人必须看：源是不是真由攻击者控制，sanitizer 会不会被编码绕过，这条路径能不能在默认配置走到。做不到这三步，状态保持 hypothesis。

## 补丁 diff

有漏洞版本和修复版本时，先看 diff 改了哪些检查，再问三个问题：

1. 修复是在所有入口上，还是只在其中一个调用点加了长度或权限检查。
2. 同一函数的其他参数、其他格式分支、32 位路径有没有被漏掉。
3. 修复是否只挡住了公布的那一种输入形状，相邻的整数宽度或编码仍能到达同一拷贝。

二进制用 BinDiff 或 Ghidra 的版本对比对齐函数。对齐错了会把无关改动当成补丁。以调用图和字符串引用核对，不以相似度百分比当结论。

不完整修复是高优先级候选：补丁说明开发者承认这里要检查，而兄弟路径没有同样的检查。

## 变体分析

步骤：

1. 用已确认的缺陷写出源、sink、缺失的检查。不要把样本输入写进规则。
2. 在同一仓库跑查询，列出其他到达同一 sink 且缺少同一类检查的路径。
3. 对每条结果做一次可达性复核。构建系统关掉的文件、测试代码、仅在 `ifdef` 调试路径里的命中单独标出。
4. 跨仓库时只复用模式，不复用结论。每个仓库重新复核。

自动化变体（CodeQL 安全查询、Semgrep 规则库）是召回工具。它们增加候选，不增加确认。

## 二进制上的污点

没有源码时，污点从系统调用、文件读、网络读进入，跟踪到拷贝、分配、间接调用或危险库函数。LLM 辅助的二进制污点（如 LATTE）把一条数据流切成按函数的小段再问模型，用来降低一次性看完整二进制的漏报。模型输出仍是 hypothesis：必须能指到具体指令或伪代码，并且最好用动态输入验证。

反编译器会丢类型和间接调用目标。查询没报，不等于没有漏洞。

## 依赖

SCA 只回答「声明的版本是否落在某个已公开漏洞的版本区间」。接下来必须看本项目是否调用到公告里的函数或配置。只出现在 SBOM 里、调用不到受影响代码的，标成「版本受影响但当前不可达」，不要写成已确认漏洞。

私有补丁或只修了上游一个调用点时，回到上一节的 diff 问题。
